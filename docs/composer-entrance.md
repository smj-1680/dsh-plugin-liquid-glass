================================================================================
  DSH 液态玻璃插件 —— 入场动画机制说明
================================================================================

  这份文档只讲一件事：**输入框的入场动画是怎么工作的，以及为什么必须是这个形状**。
  改动画之前请先读完，否则很容易重犯下面记录的错误。


================================================================================
【一】最终效果
================================================================================

  输入框**每次由隐藏变为可见**时，都会播一次入场动画：

      opacity 0 → 1，同时 translateY(20px) → 0
      时长 800ms，曲线 ease-out，animation-fill-mode: backwards

  触发场景：应用启动、手动点"新会话"(Ctrl+N)、切换会话 —— 全部都播。
  （早期版本试图区分"启动=恢复会话所以不播 / 新会话才播"，
    结果因为应用启动落在哪个页面本身不稳定，导致时有时无，该思路已废弃。）


================================================================================
【二】三层结构：为什么动画不能直接加在输入框上
================================================================================

  输入框元素自带 backdrop-filter: blur(26px) saturate(210%)。

  ★ 硬约束: 给带 backdrop-filter 的元素做 opacity/transform 动画，
    Chromium 会把它提升为独立合成层，**backdrop 采样被打断**，
    动画期间玻璃会消失或闪烁。

  所以职责被拆到三个元素上：

    ① 卡片 (RlGAzG_card)，带 backdrop-filter，承载**材质** —— 永不动画
    ② 座位 (卡片的父节点)                        —— 承载**入场动画**(translateY + 淡入)
    ③ 闸门 (body.dsh-glass-ready 类)             —— 控制**可见性**(opacity 0 ↔ 1)

  淡入在卡片上、位移在座位上，两者不冲突；闸门未开时卡片 opacity:0，
  所以"等待材质"这段时间是不可见的。


================================================================================
【三】闸门：为什么需要它，以及它匹配什么
================================================================================

  3.1 为什么需要
  ------------------------------------------------------------------------------
  应用在 ~900ms 就画出输入框，而插件的样式表与脚本要到那时才生效。
  如果不做处理，用户会先看到一个**无材质、无动画的原始输入框**，然后它才"变成玻璃"。

  缩短这个时间不是解法（静止态依然存在，只是更短）。
  解法是把输入框**先藏起来**，等材质就绪后连动画一起亮相。

  3.2 闸门匹配哪些元素（★ 这里踩过两次坑）
  ------------------------------------------------------------------------------
  闸门**同时**用两类选择器，缺一不可：

    a) [data-dsh-glass="composer"]
       —— 插件运行时打上的标记。稳定，但**首帧时还不存在**。

    b) [class*="_card"]:has([contenteditable="true"]),
       [class*="_card"]:has(textarea),
       *:has(> [class*="_card"] > [contenteditable="true"])
       —— 结构性匹配，**首帧就能命中**。宽泛规则全部被
          body:not(.dsh-glass-ready) 限制在启动后约 1 秒内。

  ★ 只写 (a) 的后果: 输入框出现到打标之间约 0.9 秒，闸门匹配不到它，
    用户就看到无材质的第一帧。（这是坑一）

  3.3 闸门绝不提前超时打开
  ------------------------------------------------------------------------------
  曾经用定时器到点就开闸门，结果**制造了它要消除的 bug**：
  如果材质比定时器慢，闸门先开 → 无材质的输入框暴露 → 之后动画才播。

  现行保险（都为"永不显示"这一最坏情况兜底）:
    · 插件一打标就开闸门（client.js: revealComposer）
    · bootstrap.js 12 秒保险丝：仍未解锁就强制显示（无动画）
    · prefers-reduced-transparency → 立即显示
    · prefers-reduced-motion → 保留显示，去掉位移


================================================================================
【四】标记必须在节点插入的**同一刻**落下
================================================================================

  这是全篇最重要的一条。

  4.1 问题
  ------------------------------------------------------------------------------
  点"新会话"时，应用把输入框**换成全新的 DOM 节点**。
  新节点没有 data-dsh-glass="composer" 属性 —— 而闸门(a) 正靠它。
  而扫描节奏在启动结束后已退化为:
    MutationObserver 140ms 防抖（流式时 40ms）/ 2.5 秒兜底轮询

  时间线实证（修复前）:
    +1170ms  new-session:started          ← 切到新会话
    +2244ms  client:composer-marked       ← 约 1 秒后才打上标记
  → 这 1 秒里，新输入框没有任何标记，闸门匹配不到，用户看到无材质第一帧。

  4.2 解法
  ------------------------------------------------------------------------------
  在 MutationObserver 回调里**同步**调用 adoptComposerNode(node)：
    · MutationObserver 回调在同一次 DOM 变更任务内执行，**早于浏览器绘制**
    · 判定条件与 markComposer() 完全一致，避免两套规则漂移:
        含可编辑元素 / 圆角 > 4px / 宽度 > 300 / 有底色或边框
    · 命中即打标，并记录 client:composer-adopted

  修复后实证:
    +2336ms  client:composer-adopted
    +4771ms  client:composer-adopted
    +6235ms  client:composer-adopted   …  此后每次新会话都命中

  ★ 教训: "选择器怎么写" (三.2) 和 "标记何时落下" (四) 是**两个不同的轴**。
    只改选择器永远修不好新会话这条路，因为新节点是运行时动态创建的。


================================================================================
【四之二】启动时不显示"被恢复的会话"（消除回跳闪烁）
================================================================================

  4b.1 问题
  ------------------------------------------------------------------------------
  应用启动时先**恢复上次的会话并渲染出来**，之后 lib/client.js 才把它切走。
  实测时间线:
    +1182ms  new-session:started
  在这之前，旧会话已经画在屏幕上了 —— 用户看到的是
  "旧会话闪一下 → 跳走 → 新会话页"，也就是"回跳"。

  4b.2 解法：既然迟早要换掉，就别让它显示
  ------------------------------------------------------------------------------
  bootstrap.js 从**首帧**起就盖住转写区:
    body:not(.dsh-glass-new-session) [class*="scrollBody"],
    body:not(.dsh-glass-new-session) [data-dsh-card="conversation"]  { opacity: 0 }
  等新会话真正接管并**稳定下来**之后，由 client.js 加上
  body.dsh-glass-new-session 揭开（220ms 淡入）。

  4b.3 揭开时机（不能"调用后立刻揭"）
  ------------------------------------------------------------------------------
  lib/client.js 调 startSession() 之后立即揭开会暴露交接的中间态，
  所以改为调用 `window.__dshGlassArmTranscriptReveal()`：
    · 监听转写区变化（childList/characterData）
    · 连续 320ms 无变化 → 判定"交接已稳定" → 揭开（via: settled）
    · 700ms 完全没动静 → 提前揭开（via: initial-quiet）
    · 2600ms 仍未稳定 → 强制揭开（via: cap）

  4b.4 三道保险（转写区绝不能永久隐藏）
  ------------------------------------------------------------------------------
    · startSession 抛错 → 立即揭开（via: start-failed）
    · 用户在 bootstrap 里被禁用（__dshGlassForceNewSession = false）→ 立即揭开
    · bootstrap 12 秒保险丝 → 揭开转写区并显示输入框（via: bootstrap:fuse-fired）

  4b.5 观感代价（用户已知情并接受）
  ------------------------------------------------------------------------------
  启动时会有一段约 1 秒的空白（转写区隐藏期）。这段空白**本来就是**要用于未来
  splash / logo 飞入动画的舞台。用户选择了"纯隐藏"方案（A），未加占位骨架。

【十一】根因定案：闸门与入场被拆成两拍（已修，2026-01）
================================================================================

  现象（用户原话）:
    "在动画的前一帧，在起始点会有一个输入框消失后又出现的问题"
    "只有输入框出现（有效果）"

  真实机制（三轮逐帧取证，startup-timeline.log 实锤，非推断）:

    时刻         证据                                            含义
    ~800ms       cardOpacity=0                                   卡片确实不可见
    ~950-1100ms  cardOpacity 0→0.4，transitionProperty=opacity   闸门开，220ms 淡入把它画了出来
    ~4100ms      probe-entrance-soon why=owed-to-transcript      入场被判"欠给正文揭幕"，没播
    ~5700ms      probe-entrance-run（seatOpacity 0→1）            入场**此时才**开始

    即：输入框约 1.0 秒就以"有材质、停在起始位置"的姿态出现，
    然后**静止约 4.5 秒**，入场动画约 5.7 秒才播。

  为什么早先几轮"抑制过渡"的修复必然无效:
    抢帧的不是卡片上的 transition —— 卡片的 transition 里**根本没有 opacity**；
    真正把卡片画出来的是**闸门规则自带的 `transition: opacity 220ms`**
    （bootstrap.js 关键 CSS / 50-glass-surfaces.css:216-227）。
    那是"闸门打开"这件事本身的效果，改卡片选择器打不到它。

  真正的缺陷: **可见性有两个来源，且不同拍。**
    · 来源一：闸门类 body.dsh-glass-ready（自带 220ms 淡入）—— 负责"可见"
    · 来源二：seat 上的入场关键帧 —— 负责"动效"
    闸门先开，动效被推迟到 deferEntranceUntilQuiet 放行时才播；
    而那条路径要等"会话切换落地"或 4 秒兜底超时，于是留下约 4.5 秒静止帧。

  修复: revealComposer 打开闸门的**同一帧**立即调用
        playComposerEntranceSoon('resume', true)
    第三个参数 immediate 让入场不再交给正文揭幕，而是当场播放。
    可见性因此只剩一个来源：闸门一开，动效同帧开始。

    为什么可以不再延后：延后原本是为避免"动画播在一个即将被替换的 composer 节点上"，
    但取证显示启动时该节点**并没有被替换**（composer 在切换被请求之前就已挂载），
    延后没换来任何好处，只换来 4.5 秒静止。

  保留的兜底（不要删）:
    · revealComposer 里"切换进行中就扣住闸门"的分支：真正的会话切换仍需要它；
    · bootstrap 12s 熔断、armTranscriptReveal 的 waitForGate 轮询。

  诊断脚手架（验证通过后可整体移除）:
    client.js 顶部的 fp 逐帧探针、markGateOpen()，以及
    client:probe-gate / client:probe-entrance-* / client:frame-* 事件。
    它们只读、不改行为；撤除时连同这些事件一起删。
